## 改了什么，为什么这样设计

[候选完整源码](../history/EXP-023/op_kernel/fire_candidate_decode_fusion.cpp)只增加 FIELD_STRIDE=712。TILE_N仍704；fieldBuf分配14*S，各fv/fvP槽位改用S，输出索引两个系数同步改变。其余六文件逐字等于22。

设输出展平位置i，候选k=floor(i/5)、字段f=i%5，源FP32字节偏移必须为4*(f*S+k)，等价4*S*i-4*(5*S-1)*floor(i/5)。因此改内部字段间距不改GM输出连续顺序；尾块也必须沿用S而不是count。

这检验的是片上地址间距这一假设。没有改变GM流量、Gather次数、浮点算式与顺序、T、分核、队列和Process，不能从源码预计提速。每槽多8个FP32元素，14槽增加448B；显式UB变为FP16=169408B、FP32=186304B，不包含编译器隐含资源。保留32B槽位对齐不构成硬件Bank映射证据。

## 验证范围

本地CPU模型穷举count=1..704和8次batch复用，共5632组标签/寻址检查。两种输入dtype使用同一FP32字段布局，不虚算为两套设备测试。输出索引和完整表前缀一致；各槽未用区哨兵与槽6～10、12持久系数保留；故意漏改输出跨度的负控被拒绝。int32最大中间值46127052，输出最大字节偏移14204，无模型越界。把布局变量还原后，与22源码全文相同。

这些检查不模拟真实DMA、异步事件或数值指令。设备正确性仅以Judge实际12点Pass描述，不能外推为全部合法输入的证明。没有真实profiler，也不把短点/长点猜成具体B/N/dtype。

## 今晚可以学到什么

1. Tile容量、字段间距、有效count是三个不同量，索引必须匹配各自单位。
2. 纯布局改动也可能让不同负载朝不同方向变化，均值会掩盖取舍。
3. 源码不变的原版仍需新对照；历史最低点不能替代今晚测量。
4. 不采用也是有效研究结果：保留源码、逐点表、假设和反例，避免重复踩坑。
