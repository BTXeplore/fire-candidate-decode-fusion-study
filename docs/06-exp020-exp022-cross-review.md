## 2. EXP-020：少做一路score倒数

令`d_i=1+exp(-z_i)`。原score为`(1/d_4)*(1/d_5)`，实数域等价为`1/(d_4*d_5)`。四路几何仍计算`1/d_i`，不改写宽高公式，避免无上界priors放大新的中间溢出风险。

仅count=704时走新路径：原Exp/Adds生成六路交错分母sigB；六次Gather拆到fieldBuf前六段；两路score分母相乘覆盖第4段；`Div(sigA,ones,fv,5*T)`生成连续五路结果。Div的三个操作数是独立申请，无新的原位覆盖要求。几何解码在sigA进行，输出Gather也读sigA；完整块ones已初始化6T项，因此5T项Div没有未初始化空洞。

尾块保留原6count项Div及score乘法，输出Gather读取fv。两条LocalTensor条件选择均是同类型句柄选择：完整块result=sigA/gatherSrc=sigB，尾块result=fv/gatherSrc=sigA。六路Gather只写fv第0–5段，priors第6–10及12段不被覆盖；第11段临时量亦独立。固定输出索引只读取每字段有效count项。

完整块Div元素数由4224降至3520，Gather次数、score乘法次数与UB申请保持。**这只减少该阶段约1/6元素，不等于总时延减少1/6。** 依赖顺序、分支和实际完整块命中率都可能影响结果；不假定Judge隐藏核数或输入形状。

### 精度、溢出与CPU覆盖

全部中间运算仍为FP32，FP16只在最后转换。新旧舍入次序不同，不保证逐位相等。按IEEE/CPU模型分母≥1，乘积没有新增Inf×0或0/0；分母乘积可能先上溢，将约小于3e-39的score归零，绝对差远小于1e-5。(-45,-45)已被明确测试：原score约8.194e-40，新score=0，不能误称CPU扫描漏掉此类情况。

实际CPU检查：FP32轴3369值、11,350,161对；FP16可表示轴3104值、9,634,816对，包含极大有限输入、±88/90、零附近、不对称和FP16邻值。样本内无容差失败；FP32 score最大绝对差1.1920928955e-7，FP16最终转换后最大差0.00048828125。另有592个完整解码/地址案例，覆盖B=1..8、两dtype、1/8/20/40核划分假设、T与cores*T邻点及N=32768，包含26,568完整Tile和30,456尾Tile；模型几何逐位一致、尾块五字段逐位一致，输出两端32项哨兵保持。

这些是实际样本与模型结果，不是全域设备误差上界。NumPy Exp/Div和共同FMA近似模型不建立NPU算术证据。020本轮12点已Pass，也不能证明未测极端输入的全部设备行为。

## 3. EXP-022：一次生成索引，减少首次构建调用

Gemini独立回复提出复用现有6T scratch承载完整5count索引ramp，这一建议经本地容量、整数边界和生命周期检查后形成EXP-022。它并未改变精确除5公式，而是去掉原来输出索引分段构建的循环，并让raw/pri索引共享同一ramp前缀。

核心数据流：sigB作ramp，sigA作t1，idx的前两T分别存raw/pri索引，后5T先存q5再存输出索引；每条指令的源与目标区独立。对i<3520，`(i*13108)>>16`精确等于floor(i/5)，最终字节地址为`4*((i%5)*704+i/5)`。ramp/t1容量6T，实际只需5count；outIdx容量5T，raw/pri各T。

完整首次构建的源码API调用由35降至9；短块成本取决于原循环轮数，例如count≤140时原11次、新9次。**这是源码层调用计数，不是编译机器指令数或时延预测。** 单builtCount缓存等价于当前Process的四个同步增长水位；首块count是每核最大值，后续只相同或变小，缓存前缀足够。

EnsureScratch移到LoadPriors的EnQue后、DeQue前，ComputeTile重复调用删除。搬入目标是独立priors队列，scratch只写sigA、sigB、idx、ones，不覆盖fieldBuf或priors队列；这提供源码层面的搬运/计算重叠机会，不等于设备实际重叠。全部浮点数学、输出Gather和Cast原封不动，显式UB仍为FP16=168960B、FP32=185856B。

实际CPU检查：

- count=1..704全部raw/pri/out索引精确，704种完整缓存前缀与短块表一致，每条运算源/目标地址区不重叠。
- int32最大中间值46127052，scaledRamp最大9909504，scaledQ5最大9895428，输出字节地址最大14076，均不溢出。
- myN=0..32768、B=1..8共262152组模型，6232576个Tile、28046592次batch计算；262144次首次构建、5970432次缓存命中。真实Process的构建均始于builtCount=0，Duplicate目标为0且32B对齐；不把结论泛化为任意从小count增长的调用序列。
- Init、Process、LoadRaw、FlushOut与016相同；LoadPriors仅移动EnsureScratch，ComputeTile仅删该调用，其余六文件逐字节相同。

CreateVecIndex/Muls/ShiftRight/Sub/Duplicate均沿用016已有计数式重载；3520长度的新组合现已在当前Judge编译并两次12/12 Pass，但没有隐藏case的真实count，不能据此声称所有704种尾长或内部掩码路径都已上设备验证。CPU模型不证明真实事件、隐含scratch或性能。

## 4. 如何使用Gemini的交叉意见

已在用户现有Argon网页发送公开016完整kernel，收到最终独立技术回复；这里只整理经审查的技术内容，不发布账号邮箱、原始会话或截图。

采用的是“一次完整ramp生成索引”的具体建议，因其容量和整数范围可直接从本地源码验证。其他说法必须分级保留：

- “Judge有48个Vector核，因此完整Tile分支永远不命中”缺少当前环境证据。必须用真实host分核和每核myN判断，不能把假定型号当隐藏测试事实。
- “字段间距是256B倍数，因此五字段100%同Bank冲突”缺少910B/CANN9.0.0物理映射或profiling证据。地址模运算本身不证明物理Bank映射，本轮未采用该布局变更，也未叠加宽高重排。
- “vdiv(1,+Inf)在部分微码产生NaN”的断言没有对应版本与实机证据。CPU已测分母先溢出反例且误差在容差内；这不能证明硬件Inf路径，但同样不能根据未经取证的断言认定候选会Fail。
- “源码调用少26次”只适用于完整首次构建的35→9计数，短块原轮数更少；不能称为固定减少26条机器指令或保证隐藏搬运时延。

完成022实现后，已把本地证据和上述异议作为完整短反馈发回现有Argon页面，收到最终复审，集中于三项具体风险：

1. CreateVecIndex从原单次≤704扩至≤3520，非8/64对齐尾长的内部掩码、步进与恢复依然需要目标覆盖；计数式重载存在不等于每条路径均已验证。当前两次Judge Pass补充了设备证据，但未暴露真实count。
2. 借用sigA/sigB作整数scratch依赖builtCount拦截和调用点；若后续修改允许ComputeTile解算中途重入，可能破坏数据。当前模型证明每核cur单调不增、仅首块构建，ComputeTile已无EnsureScratch调用；未来改变调度时须重做此证明。
3. EnsureScratch虽移到priors EnQue/DeQue之间，仍位于首个LoadRaw之前。源码上独立priors搬运的窗口不保证覆盖了全部索引成本，也可能影响首raw发射；没有指令时间线，收益机制仍待证。

最终回复中“0.15～0.30µs背景漂移”没有提供测量来源，不作为本报告事实或误差阈值。此处只使用本轮两次原16和两次022的实际变化描述测量不稳定，不能把Gemini建议等同设备profile结论。

EXP-021的生命周期复用草稿没有设备结果。省UB不是已证明的加速机制，原017同时改变Tile也不能单独证明复用一定导致退化；本轮将名额换为更便于验证索引构建成本的022，保留原草稿，不制造其测试结论。

两项仅使用已有候选中的Exp、Adds、Gather、Mul、Div、FusedMulAdd、Cast、队列、DataCopyPad及索引基础API。没有以master/Ascend950接口证明910B/CANN9.0.0支持，也不推荐已确认不可用的Scatter、ExpSub、FusedExpSub。
